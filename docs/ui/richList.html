Including the traps the code does not reveal on its own. The concrete example throughout is the ARC Runway table (coreit-arch-inventar-app); every rule generalises to any rich, user-configurable list.

Part A — Specification

A1The building blocks at a glance

┌─ p:fieldset id="cols" legend="Display"  (toggleable, state persisted) ──────────┐
│  ┌─ Profile block ────────────────────────────────────────────────────────────┐ │
│  │ Profile: [ Default          ▾ ]  [+ New]  [🗑 Delete]   hint text           │ │
│  │                                                                            │ │
│  │ Total width:   [ 1730 px ]  [Apply ⟳]    "Leave empty means: sum of…"      │ │
│  │ Column width:  [   54 px ]               "The button in the column head …" │ │
│  └────────────────────────────────────────────────────────────────────────────┘ │
│  [All] [Default]  (+ page-specific quick toggles)                               │
│                                                                                 │
│  ☑ Summary  ☑ Key  ☑ Status  ☐ Future  ☑ Team  ☐ Type  ☑ Sprint  ☐ Repos        │
│  ☑ PI 42    ☑ PI 43  ☐ PI 44 …                     (grid, 4 columns)            │
└─────────────────────────────────────────────────────────────────────────────────┘

Table header, per column:
   ┌───────────────────────────────┐
   │ Summary        ▲   ↔  ┆┆      │   ↔  = Apply button (to the target width)
   └───────────────────────────────┘   ┆┆ = drag handle (two vertical strokes)

The drag handle is what people casually call "the dots": two fine vertical strokes at 65 % of the header height, permanently visible. Permanently is a decision, not carelessness — in the theme the handle is invisible, and anyone who does not know a column can be dragged there will never discover it.

A2Data model

One state object per user and page, stored as JSON. The display-related fields:

FieldTypeMeaning
columnVisibleMap<String,Boolean>visibility per column key; a missing entry means the page default
columnWidthsMap<String,String>CSS width including unit, e.g. owner → 180px
totalWidthIntegertotal width of the table; null means "compute from the columns"
targetColumnWidthIntegerthe value the Apply button sets a single column to
colsExpandedbooleanwhether the "Display" panel is open
profilesMap<String,Profile>named profiles
activeProfileStringthe profile applied most recently

A profile is a snapshot of exactly four of these fields: columnWidths, columnVisible, totalWidth, targetColumnWidth. No more — filters, sorting and expanded rows belong to the working state, not to the display.

The column key is the contract between three places that know nothing about each other: the page (which column is rendered), the stored state (which width belongs to it) and the resize event. The last of these carries no column identifier, only the header text — so every column carries its label, and the key is recovered from the header text on resize.

A consequence you must know

Two columns of the same table must not share the same header text. Otherwise a dragged width lands on the wrong column. For dynamic columns (pi42, pi43, …) this is the only way at all — their component ID changes on every render.

A3The controls in detail

Profile selector

p:selectOneMenu, its values are the profile names. Selecting applies immediately — a separate "Apply" button would be a needless second step. On first use a Default profile is created automatically from the existing state, so that "no profile" is never active.

New / Delete

"New" opens a dialog with a name field and creates a profile from the current state. "Delete" removes only the profile; the working state stays exactly as it was. Afterwards a profile is activated again.

Automatic saving

Every change to columns or widths is written to the active profile immediately. Anyone working with a profile expects it to keep its state; a save button would be one extra action for something no one deliberately wants to discard.

Total width

A number field with the unit px, lower bound 200. Empty means: the table follows the sum of its columns and grows as you drag. A set value holds the table at that width; dragging then only moves the boundary between two columns.

Beside it, one button with two jobs, whose label moves with the situation:

SituationLabelEffect
Entered width ≠ sum of columnsApplyscales all visible columns proportionally to the value
Entered width = sum (or empty)Compute from columnsclears totalWidth; the width follows the columns again

When scaling proportionally, no column drops below 44 px. If the lower bound breaks the arithmetic, totalWidth is discarded and the user is told the smallest possible width ("At 800 px, 6 columns would be too narrow — the smallest possible width is 1042 px"). This matters more than it looks: a field showing a number that does not hold is worse than an empty one.

Column width

A second number field, lower bound 44. It is the value the Apply button in the column header sets a single column to. The reason is mundane and yet the most used part of the whole control: dragging by hand never hits the same pixel value twice. Anyone who wants twelve PI columns to be equally wide will never get them equal by dragging.

Values that are too small are discarded, not flagged

A < 200 in the total width, or a < 44 in the column width, sets the field to "empty" instead of raising a validation message. An error message on a field that only configures the display would hold up the whole form — and the user was not trying to submit anything here, only to nudge.

Column choice

A grid of checkboxes, four per row. Every change updates the table immediately and writes to the active profile. Alongside, two quick toggles All and Default; page-specific group toggles (the PI columns in ARC Runway, "LeanIX" and "Attributes" in Applications) sit next to them.

PrimeFaces 15

layout="grid" on p:selectManyCheckbox / p:selectOneRadio has been removed and throws a FacesException on render — the page stays blank, the build stays green. The same grid is produced by layout="responsive" with columns="4". Found in production, 29 Aug 2026.

Expand and collapse

The state of the panel belongs in the persisted state, not in the bean: the panel is re-rendered on every column change, and a value that only starts as "collapsed" in the bean would collapse it every time — in the middle of setting things up.

A4The width mechanics

The table runs with table-layout: fixed and is allowed to run off to the right and scroll, rather than redistributing its columns.

Why the total width has to be set at all: with table-layout: fixed the browser distributes the columns proportionally across the table width. The set pixel values thereby become mere ratios. Measured: the sum of the column requests was 1730 px, column 1 asked for 800 px and rendered at 1029 px. Only a table width equal to the sum makes the pixel values binding. The sum comes from the bean, not from CSS — a min-width: max-content stood here first and inflated the table regardless of the requests.

No white-space: nowrap on the cells. PrimeFaces sets it automatically with resizableColumns; long values then ran out beyond the set width. A counter-rule is required.

A5Handles and Apply button — the visible parts

Drag handle ("the dots")

.ui-treetable thead th .ui-column-resizer {
    width: 18px;
    cursor: col-resize;
    background: linear-gradient(to right,
        transparent 4px, #94a3b8 4px, #94a3b8 5px,
        transparent 5px, transparent 8px, #94a3b8 8px,
        #94a3b8 9px, transparent 9px);
    background-repeat: no-repeat;
    background-position: center;
    background-size: 18px 65%;
}
.ui-treetable thead th .ui-column-resizer:hover {
    background-color: #dbeafe;
    outline: 1px solid #60a5fa;
}

Two 1 px strokes, 3 px apart, centred, at 65 % of the header height. On hover the whole area colours in — so the click target is recognisable, not just the strokes.

Not position:relative on the th

PrimeFaces computes the drag position against the offsetParent; a relatively positioned th becomes its own offsetParent, and the coordinates then no longer match the table geometry — the handles are visible, but the drag does not take hold.

Apply button

.ui-treetable thead th .arc-setzen {
    float: right; width: 13px; height: 20px; margin: 0 1px 0 0;
    cursor: pointer; text-align: center;
    font-size: 10px; line-height: 20px;
    color: #94a3b8; user-select: none;
}

The character ↔ (U+2194). 13 px, because in the header of a 54 px-wide PI column the title, the sort arrow and the 18 px drag handle are already sitting next to it.

The button must intercept mousedown in the capture phase (addEventListener(…, true)) and call preventDefault + stopPropagation — otherwise a click also re-sorts the table.

Column rules

border-right: 1px solid #cbd5e1 on all header cells and body cells. They also show where the grip sits. Previously they only surrounded one sub-range, with gaps in between.

A6The reporting path to the server

Two p:remoteCommand, called from JavaScript:

NameParametersTrigger
reportColumnWidthsp = header text, px = widthApply button, drag handle of the last column
reportTotalWidthgb = widthafter every drag, once the sum has been recomputed

On the server, sp is mapped back to the column key via fromHeader(); an unknown header leads to a discard, not to storing under a made-up key.

Two mandatory settings, both dearly bought

partialSubmit="true" — without it PrimeFaces submits the whole form, and on large pages the profile name arrived empty, the column checkboxes counted as "off" one after another, and the spinner ran forever.

process="@this" — otherwise the whole form runs through validation.

A7Measured traps

This list is the real value of the document. Every point cost time once.

  1. p:treeTable has no resizeMode. The attribute exists only on p:dataTable; TreeTableBase knows only resizableColumns and liveResize. A resizeMode="expand" on the TreeTable is silently ignored. The JavaScript, however, reads cfg.resizeMode afresh on every drag — so the value has to be patched onto the finished widget and resize() replaced. Root's resize() always squeezes the neighbour, which is why a column could only be dragged as far as the neighbour gave way. With p:dataTable this drops away entirely — resizeMode="expand" works natively. That is why the rebuild for p:dataTable is much smaller than the original.
  2. The last column gets no handle. PrimeFaces creates it and hides it in "fit" mode — it has to be shown again and given its own handlers. If a new span is created without checking for the existing one, two end up side by side.
  3. height: 100% on a floated child without a parent height yields 0. The self-attached handle then hangs in the header but has no click area. Use a fixed height: 20px as PrimeFaces does.
  4. p:inputNumber puts its ID on a span. The actual fields are called <id>_input (visible, formatted, with unit) and <id>_hinput (raw). Reading the span yields undefined — the button thought it was unconfigured and did nothing. The value must come from the DOM, not from the bean: it may just have been typed and not yet submitted.
  5. After every partial Ajax update the table header is a new DOM node. Handles and buttons are then gone. A MutationObserver on document.body re-installs them — it must be guarded against itself (only insert where none exists yet) and must never throw, or the exception tears apart a running partial update.
  6. On load alone the observer is not enough. PrimeFaces builds its widgets in jQuery's ready phase, i.e. after DOMContentLoaded; the DOM does not change after that, so the observer never fires. The original's remedy: five setTimeout calls (400–2000 ms) plus a mousedown listener that re-installs reliably the first time a handle is touched.
  7. UIData.var must be a literal. A forwarded var="#{var}" throws IllegalArgumentException in UIData.setValueExpression → HTTP 500. A tag file that spans a table has to wire the row variable in directly.
  8. A tag file inherits the attributes of the surrounding tag file. Optional attributes of inner tags must therefore not share names with attributes of the outer one (rendered, styleClass, rows, emptyMessage, …) — they need a prefix. Mandatory attributes are safe, because they are always set.
  9. An unset attribute is not the same as a missing one. If a tag file contains sortBy="#{sortBy}" and someone calls the tag without sortBy, Facelets still creates an (empty) ValueExpression — PrimeFaces sees a set sortBy and makes the column sortable and filterable, complete with an input field in the header.
  10. No NamingContainer. A Facelet tag file is expanded inline while the tree is built; a composite component, by contrast, wraps its content in a NamingContainer. p:column must be a direct child of the table — which is why one way works and the other does not.

A8Checklist for a rebuild

Server side

  • state object with the seven fields from A2, storable as JSON, without framework ties
  • column description: key, header text, default width, default visibility
  • map header text → key, discard unknown headers
  • storage as an interface (load(page) / save(page, state)), not as an entity
  • lower bounds 44 px / 200 px, discard values that are too small rather than flagging them
  • proportional scaling with a lower bound and honest feedback
  • "one button, two jobs" with a moving label
  • limit the profile snapshot to exactly four fields
  • write to the active profile after every change

View side

  • resizableColumns="true" + resizeMode="expand" (with p:dataTable that is enough)
  • tableStyle = total width from the bean
  • p:ajax event="colResize" to the bean
  • make the drag handle visible (CSS from A5)
  • Apply button per header, intercept mousedown in the capture phase
  • p:remoteCommand with partialSubmit="true" and process="@this"
  • MutationObserver + a guard against exceptions
  • checkboxes with layout="responsive", not grid

B2What should be improved in the UI

1. Percentage widths on columns (≈ 300 places)

width:10% (67 ×), width:5% (51 ×), width:8% (49 ×) … Percent is the wrong unit for most of these columns: the width needed depends on the content, not on the window width. On a table with eight columns, 5 % is too little for four-digit numbers; on one with three columns it is empty space. → Pixels for columns with known content, auto for free text.

2. 1106 inline style attributes

Every change to the appearance is thereby a search across 58 files. The commonest patterns (margin-right, color:#64748b, font-size:0.85em) have long earned classes; some of them are already replaced by the inv: taglib.

3. Fifteen own global p:confirmDialog

root has provided one in the template since 1.651.0. As long as the per-page copies remain, it cannot be adopted — two global dialogs on one page are a regression. The replacement is mechanical but has to happen in one go.

4. Nine own p:growl

Same picture, same replacement.

5. The access guard is inline in the template

Instead of an access-denied page, a 30-line block sits in the forked template. root has the redirect; as long as the page is missing, the fork remains.

6. Only one page has a context menu

— and there the most-used action was missing until today. A right-click is a natural expectation on tables; where there is a row action, it belongs in the context menu too, not only in a column you first have to scroll to horizontally.

7. Two implementations of the same display control

ARC Runway (TreeTable, PI columns) and the tablestate module (DataTable) do the same thing with separate code. That happened deliberately — no one wanted to pull the TreeTable special cases into the generic path — but it remains a doubled place to maintain. With pt:tableSettings in root it becomes, for a while, three.

B4Suggested order

  1. Merge and release root PR #161 — everything else is blocked until then.
  2. Lift the app onto pt:tableSettings: includes/anzeige-einstellungen.xhtml goes away, the three pages (code, applications, projects) use the tag. In doing so the render test the tag lacks today comes into being.
  3. Consolidate global messages: 15 ConfirmDialogs and 9 Growls out, root's globalMessagesForm into the template. One go, one page of checking.
  4. Introduce pt:deleteButton — 26 places, mechanical, and the global dialog from step 3 is the precondition for it.
  5. Column tags onto the simple columns, page by page rather than in one go.
  6. ARC Runway last onto the shared path, with the TreeTable special cases as a deliberately documented exception — or not at all, if the special cases eat the gain.
  7. Percentage widths into pixel/auto, page by page, each checked visibly on one page.

Steps 3–5 are each small on their own and individually checkable. Steps 1 and 2 are the only ones with a real dependency.
